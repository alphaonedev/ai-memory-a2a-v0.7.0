# F7 — Subscription webhook SSRF guard blocks loopback URLs by default

**Status:** OPEN (config preference, scenarios need real webhook receiver)
**Severity:** P3 (deliberate security default)
**Affected (Round 1 FAIL):** S33, S59

## Symptom

S33 (`scenarios/33_subscribe_pubsub.py`) calls
`POST /api/v1/subscriptions {agent_id, namespace}` and gets HTTP 400:

    "webhook URL targets loopback address http://localhost/_ns/ai:bob/test
    — rejected by default (SSRF guard); set
    `[subscriptions] allow_loopback_webhooks = true` to opt in
    (testing / dev only)"

When the body omits an explicit `webhook_url`, the v0.7.0 daemon synthesizes
a default loopback URL and the SSRF guard rejects it.

S59 stages a webhook receiver on node-1 then subscribes; that test passes
through the same code path and gets 0 webhook deliveries because the
subscription itself was 400'd.

## Daemon assessment

This is a deliberate default. SSRF protection is a v0.7.0 hardening; the
opt-out exists. From an operator's standpoint, both options are sound:

  (a) Patch the campaign config to set
      `[subscriptions] allow_loopback_webhooks = true` (testing/dev only).
  (b) Update the scenarios to pass an explicit non-loopback webhook URL
      (e.g. node-2's private IP + a small staged HTTP receiver).

Neither belongs in this Path C topology bring-up. Filed as content-refresh
work alongside F6.

## Why we did NOT flip the daemon config

Rules of engagement: "DO NOT modify the running daemons' configs except
via established mechanisms (no ad-hoc systemctl edit outside the existing
federation drop-in)". A new `[subscriptions]` block in config.toml would
be an ad-hoc config change.
