# F5 — S76 AGE perf gate not met on s-1vcpu-1gb postgres droplet

**Severity:** P3 — environmental / threshold calibration, not a daemon defect
**Discovered:** 2026-05-09 during pgvector coverage-extension run
**Affects:** S76 (`76_age_perf_gate.py`)
**Status:** marginal failure; data + thresholds documented for future calibration

## Symptom

S76 seeds 1000 entities + 5000 edges, then runs 10 timed
`find_paths(depth=5)` queries with AGE enabled and 10 with AGE
dropped (recursive CTE fallback). The PASS gate requires AGE p95 to
be at least 1.3× faster than CTE p95. On this run:

```
age p95 = 79.7 ms     (10 runs: 61.3 .. 81.4 ms)
cte p95 = 83.4 ms     (10 runs: 62.1 .. 87.9 ms)
ratio   = 1.05x       (gate requires ≥ 1.3x)
```

Both backends complete in essentially the same wall-time band; AGE's
expected advantage at depth 5 is ~5% rather than the 30% the gate
requires.

## Root cause hypothesis

The campaign's postgres droplet is a `s-1vcpu-1gb` (DigitalOcean
basic) instance shared with AGE 1.5.0 + pgvector 0.7.4. At 1000 nodes
/ 5000 edges, the recursive CTE fits comfortably in the page cache
(roughly ~5 MB of edge data) and the planner's nested-loop join over
an in-memory hash index is competitive with AGE's traversal because:

1. CPU is single-vCPU, so AGE's specialised graph operator can't
   parallelize.
2. Working set is small enough that the cost difference between
   AGE's adjacency-list walker and PG's recursive CTE is dominated
   by per-row tuple-construction overhead, which is similar for both.
3. AGE's intermediate-result materialisation has a fixed startup cost
   that is amortised over a much larger dataset in production.

This is a **threshold-vs-host** issue, not a daemon regression.
Independent benchmark runs against AGE 1.5.0 on a 4-vCPU instance with
50k+ nodes typically show 2.5–4× advantage at depth 5 (see
`PERFORMANCE.md` § graph-perf in the source repo).

## Evidence the AGE backend is functionally healthy

S75 (schema-parity) PASSed at 1.0s — the AGE schema, Cypher views,
and pgvector-backed embedding columns are all in place. The
`sal_contract` cargo test against pg+AGE+pgvector passed 20/20 at
2.53s. AGE is loaded (`extension age 1.5.0`, namespace `ag_catalog`).

## Suggested remediation (NOT applied this round)

Either:

1. Loosen the gate to `≥ 1.1x` for the 1k-node / 1-vCPU
   matrix and add a `≥ 1.3x` gate for a 50k-node matrix that
   only runs on multi-vCPU hardware. (Test-side change; touches
   `scenarios/76_age_perf_gate.py`.)
2. Keep the 1.3x gate but increase seed size to 50k entities so AGE's
   structural advantage shows on small hardware. (Bumps wall budget
   from 10s to ~3–5 min.)
3. Add a host-class auto-detect in the scenario that selects the gate
   threshold based on `nproc` and `total_mem`.

Filing as F5 for the next campaign-repo maintenance pass; the perf
band itself (sub-100ms p95 for both backends at depth 5 on 1k×5k) is
fully consistent with the daemon's published `PERFORMANCE.md` budgets.

## Why this surfaces now

Same as F3/F4: prior runs short-circuited at the pgvector skip-gate.
With pgvector installed, S76 actually runs and exposes that the
default 1.3x threshold is too aggressive for a 1-vCPU droplet.
