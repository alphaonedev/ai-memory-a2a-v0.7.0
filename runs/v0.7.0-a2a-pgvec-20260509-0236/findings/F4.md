# F4 — S72 hardcodes wrong sqlite path for openclaw daemon

**Severity:** P3 — campaign scenario bug, not a daemon defect
**Discovered:** 2026-05-09 during pgvector coverage-extension run
**Affects:** S72 (`72_age_a2a_kg.py`)
**Status:** test-side bug; daemon behaviour unaffected

## Symptom

Phase B's `ai-memory migrate` reports `memories_read: 0` even though
Phase A successfully wrote 10 entities to openclaw's running daemon
via `POST /api/v1/memories`:

```
phase A: openclaw seeds 10-entity KG on its local sqlite
phase B: openclaw migrates → postgres aimemory_s72
  migrate stdout[:200]={
  "batches": 1,
  "errors": [],
  "from_url": "sqlite:///var/lib/ai-memory/store.db",
  "memories_read": 0,
  "memories_written": 0,
  ...
}
```

…and Phase C/D fingerprints come back empty, so the scenario reports
"hermes saw empty kg_query — migration may not have run".

## Root cause

`scenarios/72_age_a2a_kg.py:149` hardcodes:

```python
openclaw_db = "/var/lib/ai-memory/store.db"
```

But the running openclaw daemon writes to `/var/lib/ai-memory/openclaw.db`
(per `/tmp/v07-bootstrap-summary.json` → `openclaw.ai_memory.db_path`).
On the running droplet:

```
$ ls -la /var/lib/ai-memory/
-rw-r--r--  19431424  openclaw.db        ← live daemon (43 rows incl. seed)
-rw-r--r--    315392  store.db           ← empty file auto-created by migrate
```

The migrate tool happily opens `store.db` (sqlite creates it on first
open if missing) and finds zero rows because the daemon writes to a
different file.

## Suggested remediation (NOT applied this round)

Either:

1. Read the daemon db path from the bootstrap manifest at runtime, or
2. Hardcode the correct file: `openclaw_db = "/var/lib/ai-memory/openclaw.db"`

Option 2 is the minimum-diff fix; option 1 is more robust if hermes-side
analogs of S72 are added later (the hermes daemon writes to
`hermes.db`).

## Why this was hidden until now

Same reason as F3: the prior `pgvector` skip-gate fired before Phase B
ever ran. Installing pgvector 0.7.4 exposes the dormant path-mismatch.
