# F6 — v0.7.0 postgres surface lacks the SQL views + link-migration that S71/S72/S76 were authored against

**Severity:** P3 — campaign-vs-product gap; not a daemon defect
**Discovered:** 2026-05-09 during the post-F3+F4+F5 re-run
**Affects:** S71 (`71_age_cte_equivalence.py`), S72 (`72_age_a2a_kg.py`), S76 (`76_age_perf_gate.py`)
**Status:** test-side gap; scenarios self-skip with full RCA. Re-enable when v0.7.1 lands the missing views + migrate-links.

## Summary

After F3/F4/F5 were investigated as "test-side issues, easy fixes," it became clear during the actual fix attempt that S71/S72/S76 share a deeper, structural blocker: they were authored against a postgres surface that v0.7.0 does NOT ship. F3 (S70) and the F4 path-discovery helper (`Harness.node_db_path`) ARE genuine test-side issues that we did fix; the rest are scenario-vs-product mismatches.

## Three concrete gaps in the v0.7.0 postgres surface

### Gap 1 — `kg_query_view` / `kg_timeline_view` / `kg_find_paths_view` SQL views are not in postgres_schema.sql

S71/S72/S76 all probe these views via raw `psql -tA -c "SELECT ... FROM kg_query_view ..."`. Direct inspection of the live postgres-node `aimemory` db at the time of the re-run (`\dv` returned "Did not find any relations") confirms they are absent. Inspection of `/Users/fate/v07/v07-fixes/src/store/postgres_schema.sql` confirms only the relational tables (`memories`, `memory_links`, `entity_aliases`, etc.) are created at adapter init — no views.

The KG operations (`kg_query`, `kg_timeline`, `kg_invalidate`, `find_paths`) ARE implemented, but as Rust SAL methods on `PostgresStore` (e.g. `kg_query_cypher` at `src/store/postgres.rs:441`, `kg_query_cte` at `src/store/postgres.rs:543`). They route inside the running daemon — there is no SQL-view alias.

### Gap 2 — `ai-memory migrate` does not iterate `memory_links`

S72's central premise is "openclaw migrates a 10-entity / 20-link KG to postgres → hermes reads the same KG via a different droplet's psql." But `src/migrate.rs::migrate` only walks `from.list(...)` (a `Vec<Memory>`) and writes via `to.store(...)`. There is NO `from.list_links(...)` step and no `to.store_link(...)` call. Verified by full-file grep of `/Users/fate/v07/v07-fixes/src/migrate.rs` for `link|Link` — zero matches.

Net effect: even with pgvector + AGE installed (which we now have), S72's Phase B forward migrate produces 10 memories on postgres + zero links. Phase C/D fingerprints are then trivially empty.

### Gap 3 — no `ai-memory schema-init` CLI verb

S71/S76 both invoke `ai-memory schema-init --store-url <pg_url>` to bootstrap their disposable test dbs (`aimemory_kgtest`, `aimemory_perf`). But `ai-memory --help` on the deployed binary (commit `e0d2086`) does not list `schema-init`; only the `migrate` subcommand currently uses `PostgresStore::connect` (which is the path that runs `INIT_SCHEMA`).

A workaround we explored — drive `PostgresStore::connect` via a no-op migrate from an empty sqlite — does run the bootstrap schema (memories, memory_links, etc.) but does NOT bootstrap the `memory_graph` AGE projection. The projection is created lazily by `kg_query_cypher` on first invocation, and only when invoked through the SAL adapter; psql cannot trigger it.

## What is honestly NOT fixable in this pass

S71, S72, S76 self-skip with the rationales above. Each scenario emits a `skipped=true` JSON record with a verbose `reason` field, so coverage telemetry remains accurate.

## Suggested remediation (campaign-side, future)

Option A (preferred for v0.7.1+): when the v0.7.1 daemon supports `--store-url postgres://`, rewrite S71/S72/S76 to drive the SAL adapter via the daemon's MCP/HTTP surface. This is the canonical path — fingerprints become "what does memory_kg_query return through the daemon?" rather than "what does this raw view return?".

Option B (interim for v0.7.0 if we want any in-scope PASS on these slots): write a tiny Rust binary in `scripts/age-cte-probe.rs` that links against `ai-memory` as a library and drives `PostgresStore::kg_query_cypher` / `kg_query_cte` directly, then call THAT from the python scenarios. This is essentially what `tests/age_cte_equivalence.rs` already does.

Either path is **out of scope** for the current "fix what you can in 60 min" remit.
